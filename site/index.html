What it does that a reviewer bot doesn't

  1. It caught a change that is green everywhere and fixes the wrong bug.

    Change 2234 passes its build, its new tests and the full suite, and a reviewer says every requirement is met. Countersign routes it to its owner with the reason: the reported regression isn't on this base.

    Walk through it

  2. Tests have to prove they test something.

    Fail-without-fix: we revert the source, keep the new tests and run them. A test that still passes on the old code doesn't count as evidence for the change.

  3. One reviewer can never clear a change.

    We measured it: given passing test results, Codex went from 4 of 11 clauses met to 11 of 11, with 0 findings. On the same changes Claude raised 13. So a clause is proven only when every reviewer agrees with verified citations.

Where it stops

  • It can't judge intent: whether this is the change the product needs.
  • It is only as good as the requirement text. Ours are placeholders derived from the upstream issues (official: false).
  • Checks ran on net8.0 / Linux only; other targets are listed as not checked in every pack.
  • Reviewers share training data, so their independence is partial; seeded bugs measure what they miss together.
  • Spot-checks, escapes and review minutes in the trust demo are simulated, and labelled so.
